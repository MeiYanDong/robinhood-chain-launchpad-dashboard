# Pons / Long / PAIR 平台活跃度

## 要回答的问题

平台活跃度不是“谁交易量最大”，而是“这个平台最近的成交，相对它自己平时放大了多少”。
因此 Pons、Long、PAIR 分别建立自己的历史基准，不把体量差异混成一个综合分，也不直接进入
PAIR/PONS 价格估值。

## 计算口径

对 7 日或 30 日窗口，先计算截至某个闭合 UTC 日的平均每日成交量：

```text
窗口日均成交量 = 窗口内完整日成交量之和 / 窗口天数
活跃倍数 = 窗口日均成交量 / 此前同周期日均成交量的历史中位数
```

“此前”有严格边界：历史样本必须在当前窗口开始前结束，避免把当前热度同时放进分子和基准。
基准最多使用最近 90 个完整的同周期样本，至少需要 30 个样本才发布倍数。

- `1.0×`：约等于该平台自己的历史常态；
- 低于历史 P25：清淡；
- P25–P75：常态；
- P75–P90：活跃；
- 高于 P90：异常活跃。

百分位和倍数描述成交是否放大，不代表项目质量、价格方向或买卖建议。

## 数据质量规则

- 只使用已经闭合的 UTC 日，默认目标日是 T-1；
- 缺失日不补零，窗口不完整就不计算倍数；
- 被标记为 `suspect_zero` 的原始零值保留在日度序列，但不进入加总、份额和基准；
- 7 日与 30 日的三平台份额，只有三者覆盖同一完整窗口时才计算；
- “上线以来”从首个已验证日展示。优先使用来源采集时点的官方累计值；只有日度账本完整时才使用
  截至最近闭合日的日度和，否则只显示已观测下限；不同上线日期之间不计算累计份额。

当前来源沿用采集账本：Pons 和 PAIR 使用各自官方 Dune-backed 日度分析，Long 使用官方索引器
匹配到池子的小时成交聚合。来源不可用时状态保持 `partial` 或 `unknown`。

Pons 与 PAIR 每次刷新都会重读官方全历史；Long 的接口按时间范围读取，因此首次接入或出现历史
缺口时运行可续跑回补器。它只补不存在的日记录，不覆盖已有值，也不把历史回补状态写成实时来源
健康：

```bash
npm run backfill:platform-activity -- --from 2026-07-13 --to YYYY-MM-DD --chunk-days 1
```

默认按 1 日分片；确认来源负载较低时可调到 2–7 日，超过 7 日会失败关闭。

## 更新与接口

服务端每日 `07:10 UTC` 刷新上一闭合日的发射台账本，活跃度从同一份账本即时派生；前端每分钟
读取缓存，不主动触发采集。查询进程缓存 `GET /api/platform-activity`，响应包含：

- 三个平台从首个已验证日起的日度序列；
- 7 日和 30 日窗口交易量、覆盖率与活跃度历史；
- 上线以来的官方累计值或已观测下限；
- 基准样本数、当前状态、百分位分档和三平台可比窗口份额。

新平台历史不足时先显示窗口与基准进度；达到 30 个合格基准样本后才自动发布倍数。
