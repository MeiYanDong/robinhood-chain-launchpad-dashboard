# RHC Launch Ledger DeBox Bot 产品规格 v0.1

- 状态：产品方向已确认，允许继续设计；尚未授权写代码、创建 Bot 或修改线上服务
- 确认日期：2026-08-30
- 产品范围：DeBox 内的只读 RHC Launchpad 数据查询 Bot
- 当前事实来源：Launch Ledger 的现有数据服务、数据质量字段和来源健康状态

## 1. 一句话定义

RHC Launch Ledger Bot 是一个 DeBox 原生的只读数据分析助手：用户用大白话询问 Robinhood Chain Launchpad 的交易量、用户费用、平台收入、排名和数据来源，Bot 用同一套 Launch Ledger 数据给出可追溯回答。

它是现有 Dashboard 的对话入口，不是第二套采集系统，也不是交易机器人。

## 2. 已确认的产品决策

1. MVP 只做按需查询，不做定时推送、被动监听或交易执行。
2. Bot 只读取现有 Launch Ledger 的权威数据，不复制 collectors 和数据库。
3. 封闭测试采用 DeBox 私聊和明确 `@Bot`，收消息使用 Long Polling。
4. 使用混合 AI：模型只把自然语言转成白名单查询；数字和结论由确定性逻辑生成。
5. 默认不保存原始聊天，只保留聚合使用指标；问题样本必须经用户主动同意并脱敏。
6. 正式 Bot 由专用项目账号持有；先封闭测试并积累证据，再申请发布和 Grant。

## 3. 用户与核心任务

### 3.1 首批用户

- 想快速了解 RHC Launchpad 活跃度的 DeBox 用户；
- 想比较平台交易量、费用和收入的研究者；
- 需要向社区解释数据口径和来源的群管理员或项目方。

### 3.2 用户真正要完成的事

1. 找出某个时间窗口内表现靠前的平台。
2. 查看单个平台的核心指标和变化。
3. 判断一个数字是官方上报、推导值、部分数据还是未知。
4. 判断今天看到的是最新完整数据还是过期缓存。

## 4. MVP 对话能力

### 4.1 指令入口

| 指令 | 用途 | 示例 |
| --- | --- | --- |
| `/rank` | 查看平台排名 | `/rank 7d volume` |
| `/platform` | 查看单个平台 | `/platform LetsCash 30d` |
| `/why` | 解释空值、口径或来源 | `/why Bankr income` |
| `/status` | 查看数据日期和来源健康 | `/status` |
| `/help` | 查看支持的问题和示例 | `/help` |

用户也可以直接说“最近 7 天哪个平台交易量最高”。自然语言入口最终必须落到上述白名单能力之一。

### 4.2 白名单查询计划

自然语言解析层只能产生以下字段：

```text
action: rank | platform | explain | status | help
window: 1d | 7d | 30d
metric: volume_usd | user_fees_usd | protocol_income_usd
platform: 已配置的规范平台 ID 或 null
language: zh-CN | en
```

解析结果不合法、平台有歧义或用户问题超出范围时，Bot 应展示可选项或说明暂不支持，不能自由调用网络、执行任意工具或猜测答案。

## 5. 回复协议

每条数据回复按以下顺序组织：

1. 一句话结论；
2. 数据截止日期和时间窗口；
3. 核心数字或排名；
4. 数据质量：`reported / derived / partial / unknown`；
5. 必要时显示范围或来源警告；
6. HTTPS 详情链接；没有 HTTPS 前不发送现有 HTTP 链接。

示意：

```text
截至 2026-08-29 UTC 完整日，LetsCash 在最近 7 天的核心数据如下：

交易量：$…
用户费用：$…
平台收入：$…

数据质量：交易量为官方上报；平台收入为推导值。
```

如果值为 `null`，统一回复“当前来源没有可比数据”，绝不显示 `$0`。

## 6. 数据与版本边界

### 6.1 唯一数据事实

Bot 读取现有 Launch Ledger 只读接口：

- 健康状态；
- 1/7/30 日总览；
- 平台明细；
- 覆盖率；
- 来源健康。

Bot 不开放刷新接口，不直接运行 collectors，不写 Launch Ledger 数据库。

### 6.2 时间口径

- 默认使用最近一个完整 UTC 日，即 T-1；
- 滚动 24 小时与完整日统计必须明确区分；
- 当前尚未闭合的日期不得进入完整日排名；
- 缓存过期或来源降级时必须在回答顶部提示。

### 6.3 版本门控

仓库记录显示线上仍为 0.3.0，而本地 0.4.0 Long 候选尚未切换。正式连接前必须通过线上健康检查、版本读回和代表性 API 响应确认真实状态。

Long 只有在对应版本完成线上部署并通过读回后才能出现在 Bot 的支持平台列表；不得混用本地候选数据和线上数据。

## 7. 系统边界

```text
DeBox 私聊或 @Bot
        ↓
DeBox Long Polling 适配层
        ↓
指令解析 / AI 白名单查询计划
        ↓
Launch Ledger 只读查询层
        ↓
口径、来源、质量和新鲜度校验
        ↓
确定性回复格式化
        ↓
DeBox 消息回复
```

Bot 服务和 Launch Ledger 数据服务应保持故障隔离。Bot 故障不能影响定时采集和 Dashboard；数据服务故障时 Bot 只能明确降级，不能自行寻找替代数字。

## 8. AI 安全边界

- AI 不接触 App Secret、数据库凭证或服务器管理权限；
- AI 不计算金额、不补全缺失数据、不修改来源优先级；
- AI 不生成买卖建议或收益承诺；
- 用户消息中的“忽略规则”“调用刷新”“访问其他网址”等内容一律不能突破白名单；
- AI 不可用时，斜杠指令和固定模板仍应可用。

## 9. 隐私与使用指标

### 9.1 默认不保存

- 原始私聊或群聊内容；
- 钱包地址、用户名、群 ID；
- 稳定的用户画像或跨会话行为轨迹。

### 9.2 可以保存的聚合指标

- 每日查询次数；
- 各指令使用次数；
- 查询成功率和失败原因类别；
- 响应延迟；
- 数据过期、降级和 `unknown` 出现次数；
- 无法识别的问题数量。

需要保存问题样本时，必须由用户主动点击“上报这个问题”，并在写入前移除身份、地址和群信息。

## 10. 失败与降级规则

| 场景 | Bot 行为 |
| --- | --- |
| AI 解析失败 | 展示 `/rank`、`/platform` 等可选指令 |
| Launch Ledger 无可用数据 | 明确回复暂不可用，不输出数字 |
| 有缓存但刷新失败 | 可以展示缓存，但必须标出日期和“数据可能已过期” |
| 单个来源失败 | 返回其余可用数据并列出失败来源 |
| 值为 `null` | 回复“未知/当前来源未提供”，不得变为 0 |
| DeBox 重复投递 | 按消息或更新 ID 幂等处理，不重复回复 |
| 触发频率过高 | 返回限流提示，不向数据服务放大请求 |

## 11. MVP 验收标准

### 11.1 数据正确性

- Bot 展示的数字与同一 API 响应完全一致；
- 所有回答都包含统计窗口和截止日期；
- `null`、显式 0、推导值和部分范围能够正确区分；
- 不可比、范围不一致和全套协议数据不得混入可比排名；
- Long 等功能受真实线上版本控制。

### 11.2 产品体验

- 五类指令均有清晰帮助和错误提示；
- 常见大白话问题能稳定转换成白名单查询；
- 有歧义时先澄清，不猜平台或指标；
- 不依赖 AI 也能通过指令完成核心任务；
- 初始回复只展示影响判断的核心信息，详细来源按需展开。

### 11.3 安全与隐私

- 普通用户不能触发刷新、写数据库或管理服务器；
- Bot 不具备钱包连接、签名、广播或交易能力；
- 凭证不进入客户端、回复、日志或模型输入；
- 默认日志中不存在原始聊天内容和稳定身份标识；
- 没有 HTTPS 前不发送外部 Dashboard 链接。

## 12. 分阶段推进

### 阶段 0：产品规格

- 完成本文件、标准对话样例、查询计划和验收用例；
- 不写运行代码，不创建真实 Bot。

### 阶段 1：本地原型

- 使用模拟 DeBox 消息验证解析与回复；
- 使用只读 fixture 或本地 API 验证数字一致性；
- 不连接真实 DeBox 凭证。

### 阶段 2：封闭测试

- 用户确认项目账号、正式名称、头像和简介后创建 Bot；
- 使用 Long Polling，只开放私聊和明确 `@Bot`；
- 文本优先，不申请监听群消息、订阅号或公开发布权限。

### 阶段 3：公开与 Grant

- 根据封闭测试数据决定是否增加 HTTPS、Webhook、公开发布或订阅；
- 准备使用说明、Demo、截图、路线图、隐私说明和真实使用数据；
- 用户明确确认后才能提交发布审核或 Grant。

## 13. Grant 证据清单

- 至少一项真实 DeBox API/SDK/Bot 接入证明；
- 可复现 Demo 和使用说明；
- 核心指令截图或录屏；
- 聚合查询次数、成功率、复访和响应时间；
- 数据来源、`unknown` 语义和安全边界说明；
- 里程碑、维护计划和公开路线图；
- 仓库或文档入口。

这些是申请材料，不代表 Grant 一定获批，也不代表存在固定金额或固定截止日期。

## 14. 进入真实实现前的外部决策门

以下动作必须再次获得用户明确确认：

1. 选择和准备专用 DeBox 项目账号；
2. 确认正式 Bot 名称、头像和简介；
3. 创建不可删除的真实 Bot；
4. 选择模型供应商和付费上限；
5. 配置真实 App Key、App Secret；
6. 修改线上服务、域名、TLS 或反向代理；
7. 申请监听群消息、订阅号或公开发布权限；
8. 提交 Grant 或对外发布。
